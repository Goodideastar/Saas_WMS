## 二、并发与锁

**Q: 你们系统是怎么解决库存超卖问题的？**

> 出库审核时，我用了两层锁机制：
> 1. **数据库行级锁**：审核前用 `SELECT ... FOR UPDATE` 锁定商品记录，防止并发修改；
> 2. **乐观锁**：Product 实体有 version 字段，更新时校验版本号，版本号不匹配则抛出异常，实现乐观失败重试。
>
> 入库审核同样用行级锁保护库存增加操作，整个流程在 `@Transactional` 事务中执行，保证数据一致性。

**Q: 代码里怎么用的？能讲讲具体逻辑吗？**

> 出库审核的核心逻辑：
> ```java
> @Transactional(rollbackFor = Exception.class)
> public void auditOutbound(Long id) {
>     // 1. 行级锁查询订单，锁住记录
>     OutboundOrder order = outboundOrderMapper.selectForUpdate(id);
>     // 2. 逐行扣减库存
>     for (OutboundOrderItem item : order.getItems()) {
>         Product product = productMapper.selectForUpdate(item.getProductId());
>         // 库存不足直接报错
>         if (product.getCurrentStock() < item.getQuantity()) {
>             throw new BusinessException("库存不足");
>         }
>         product.setCurrentStock(product.getCurrentStock() - item.getQuantity());
>         productMapper.updateById(product); // version 自动递增，冲突则失败
>     }
>     order.setStatus("AUDITED");
>     outboundOrderMapper.updateById(order);
> }
> ```

**Q: 生成订单号是怎么做的？**

> 订单号格式是 `IN/OUT + yyyyMMdd + 4位序号`，比如 `IN202608020001`。
> 用 Redisson 分布式锁保证高并发下单时序号不重复：
> ```java
> RLock lock = redissonClient.getLock("order-no-lock:inbound");
> lock.lock();
> try {
>     // LIMIT 1 查当天最大序号
>     int seq = inboundOrderMapper.selectMaxSeqToday();
>     order.setOrderNo("IN" + dateStr + String.format("%04d", seq + 1));
> } finally {
>     lock.unlock();
> }
> ```

## 三、缓存

**Q: Redis 在项目中用到了哪些场景？**

> 主要有三个场景：
> 1. **用户权限缓存**：登录时把用户权限列表写入 Redis（`user:perm:{userId}`），每次请求从 Redis 读取，减少 DB 查询；
> 2. **Token 黑名单**：用户退出登录时把 token 加入 Redis，设置 24 小时过期，用于 JWT 注销；
> 3. **仪表盘统计缓存**：Dashboard 统计数据用 `@Cacheable` 缓存 1 小时，库存变动时通过 `@CacheEvict` 主动失效。

**Q: 缓存穿透/击穿/雪崩怎么解决的？**

> - **穿透**：查询不存在的数据时，缓存空值并设置短过期时间；
> - **击穿**：热点 key 过期时用 Redisson 分布式锁，只有一个线程去查 DB，其他线程等待；
> - **雪崩**：过期时间加随机偏移量，避免大量 key 同时过期。

## 四、事务与 Spring

**Q: @Transactional 有哪些失效场景，你们遇到过吗？**

> 常见的失效场景：
> 1. **方法不是 public**：我们用的都是 public 方法，没遇到；
> 2. **同类方法自调用**：比如 A 方法调 B 方法，B 的 @Transactional 不生效。我们通过 Service 注入自身避免；
> 3. **异常被 catch 吃掉**：我们在 catch 块里手动 `throw new BusinessException()`，保证事务回滚；
> 4. **异常类型不匹配**：默认只回滚 RuntimeException，我们统一用 `rollbackFor = Exception.class` 兜底。

**Q: Spring 自动装配原理了解吗？**

> Spring Boot 启动时扫描 `META-INF/spring.factories`（或 `org.springframework.boot.autoconfigure.AutoConfiguration.imports`），根据 `@ConditionalOnClass`、`@ConditionalOnMissingBean` 等条件注解判断是否加载某个配置类。比如我们项目引入 MyBatis Plus 后，自动装配了 DataSource、SqlSessionFactory 等 Bean。

## 五、数据库

**Q: MySQL 索引优化做过什么？**

> 主要场景：
> 1. **出入库单分页查询**：`order_no`、`status`、`create_time` 建立联合索引，避免全表扫描；
> 2. **产品搜索**：`product_code`、`product_name` 建立索引，支持模糊查询优化；
> 3. **审核操作**：`SELECT ... FOR UPDATE` 加行锁，索引确保锁粒度最小。

**Q: 乐观锁和悲观锁的区别，你们怎么用？**

> - **悲观锁**：`SELECT ... FOR UPDATE`，查询时加锁，适合写多读少、冲突概率高的场景（出库审核）；
> - **乐观锁**：Product 实体有 version 字段，更新时比较版本号，冲突则失败重试，适合读多写少、冲突概率低的场景。
>
> 我们出库用悲观锁保证强一致，产品基础信息修改用乐观锁减少锁竞争。

## 六、JWT 与权限

**Q: 你们的鉴权方案是怎么设计的？**

> 登录成功后生成 JWT token 返回前端，前端存在 localStorage，每次请求带 `Authorization: Bearer <token>`。
> 后端通过 `JwtAuthenticationFilter` 拦截请求：
> 1. 解析 token 获取 userId；
> 2. 从 Redis 读取用户权限列表（`user:perm:{userId}`）；
> 3. 设置 `SecurityContext`，Controller 方法用 `@PreAuthorize("hasAuthority('product:add')")` 控制权限。

**Q: Redis 里权限数据什么时候更新？**

> 用户权限变更（管理员修改角色）后，调用 `authService.refreshUserPerms(userId)`，先删除 Redis 中的旧权限 key，再重新写入。下次请求时从 DB 加载最新权限。

## 七、微服务（加分项）

**Q: 你们项目是单体还是微服务？了解微服务吗？**

> 目前是单体架构，部署在一个 Spring Boot 应用中。
> 我了解 Spring Cloud Alibaba，核心组件：
> - **Nacos**：服务注册发现和配置中心；
> - **OpenFeign**：声明式 HTTP 调用，像调本地方法一样调其他服务；

## 八、部署与运维

**Q: 你们怎么部署的？**

> 用 Docker Compose 一键部署，`docker-compose.yml` 定义了四个服务：
> - `mysql`：数据库，数据卷持久化；
> - `redis`：缓存，开启 AOF 持久化；
> - `backend`：Spring Boot，依赖 MySQL 和 Redis 健康检查后启动；
> - `frontend`：Nginx 托管 Vue 静态资源，反向代理 `/api` 到后端。
>
> 云服务器上用阿里云安全组开放 80、443、8080 端口，部署后通过 `http://服务器IP` 直接访问。

**Q: 遇到过什么问题，怎么解决的？**

> 部署时 AI Gateway 报 JSON 解析错误：`Expecting value: line 1 column 1 (char 0)`。
> 原因是 LLM 返回的内容不是纯 JSON，可能包含 Markdown 标记或多余文字。
> 修复方案：在 `nodes.py` 中增加容错解析逻辑，用正则提取 JSON 块，并在 LLM 返回无效时启用兜底计划（根据用户消息关键词自动推断工具调用）。
